# 栅格格式与导出交付设计

## 基线与范围

固定上游 commit `4e7a17cd5d5723313f459753663d0d155f047e19`；已提交实现 `bdc3c0847fa7d2ed5db82128dafcf3f47ad1bfa1`。范围逐项列于 [scope.md](scope.md)，每个 U 组的子能力都需拆成实现时的命令/参数/操作记录，不以一组一个按钮结案。

同级前置：无新增同级 change 的硬依赖。相邻模块只是消费端口的软依赖时，以现有内核能力完成基础流程，新增联动在两边均交付后验证。原 change 的未验收项仍按其证据处理；本计划仅追加缺口，不自动勾选或重写旧任务。

## 操作与布局

文件 → 打开 / 导出 / Save for Web 与图层快速导出；使用前置结构 change 的字节、候选注册和交付端口，不改文档生命周期实现。

复用固定上游 0.9.0 的生产算法，不修改 vendor。`rust/crates/editor-core` 持有规范内容、命令、预览草稿、身份与历史；`packages/protocol` 持有纯数据和限额契约；`packages/editor` 持有共享工具/面板。`dev` 与 `integrations/woohaa` 只装配公共端口，核心不得 import Woohaa 私有实现或内部工具。

界面沿用既有菜单 → 工具组 → 参数栏 → 原图/属性反馈的结构，菜单和参数栏在文档标签之上。所有状态均需有可见忙碌、失败与恢复反馈；面板仍使用现有浮动/停靠能力，不重新设计外壳。只验收电脑 1440×1000 和 Pad 正常窗口 1024×768；手机/极窄窗口和无障碍专项不在范围。

## 本域实现决策

### D1

只持有格式矩阵、编码候选和交付批次；文件文档注册、来源/保存基线、关闭结算通过前置 change 的稳定端口调用。打开验证成功才注册；当前文档和保存基线不因编码导出改变。

### D2

按实际 WASM 构建维护读/写/元数据/颜色位深支持矩阵。第一步接 RGB/U8 的 TIFF/GIF/BMP/TGA/ICO/QOI/PNM/PCX/XPM/DDS 中经验证可用项；FITS/DPX/Cineon/EXR 仅在存在无损兼容路径时开放，否则明确列为暂缓；AVIF/HEIF 以 feature 和运行时探测为准。不得自动降位深。

### D3

每个编码器返回字节/MIME/尺寸/损失报告，统一由宿主字节交付；逐层/名称资产的布局与有界命名打包属于本模块，不开启后台监听。参数预设使用本模块版本化存储，不与文档创建预设共用可变配置对象。

### D4

通用 codec 端口属于前置契约；本 change 提供静态图像实现，动画模块提供自己的时序媒体实现，互不修改对方 registry。原生路径和未编入 WASM 的格式拒绝。

### D5（实施记录：菜单落点与宿主格式清单）

两处跨层的「谁说了算」在实施时定案：

- **菜单落点**：共享「文件」菜单只加两条**可选**回调（`onExportRaster` / `onExportWeb`）并向本域
  发送「打开本域面板」的意图；页签、模式与设置重置归本域（`features/io/menu-request.ts`，
  以 nonce 做一次性消费）。共享层因此不需要理解本域的 tab/mode 语义，也不会在用户切换后再次
  覆盖。
- **宿主格式清单**：`<input accept>` 在首帧就要有值，而 `openAccept()` 依赖内核实例，只能异步
  取值。故静态清单（`OPEN_RASTER_EXTENSIONS` / `OPEN_RASTER_MIMES` / `OPEN_RASTER_ACCEPT`）落在
  协议域一处，宿主直接引用；它与内核矩阵的一致性由真实产物断言钉住，避免出现「两份清单各自
  漂移」。暂缓格式一律不入列：放进去只会让用户选中后立刻被拒绝。
- **交付端口归属**：域面板产出内存字节，落盘归宿主。dev 与 Woohaa 的浏览器下载都只能报
  `download-started`，**不得**据此推进保存基线；「导出 PNG」与「保存工程」是两条路径，
  前者永不改基线。宿主必须真的注入交付端口——缺端口时菜单仍会渲染，所以「端口是否注入」
  必须由断言而不是由菜单文案来保证（`dev/src/dev-controller.ts` 的 `devControllerOptions()`
  就是为此把装配从 JSX 里抽出来的）。
- **置入与打开共用一份清单**：内核 `place_asset` 与打开走同一套 codecs，因此「置入图片…」的
  accept 也由 `OPEN_RASTER_ACCEPT` 派生。两边各自维护，就会出现「能打开却选不中置入」的
  割裂体验。

## 事务和生命周期

内容操作遵守 begin → preview → commit/cancel：固定 documentId/generation、baseRevision、目标及 attemptId；预览不变正式内容 hash/修订/历史，确认最新有效候选一次，取消恢复，无变化不新增历史。非法参数不得确认上一份成功预览。一次笔迹/拖动按既有完成规则提交，不强制所有参数都变成弹窗。

保存、切文档、关闭、只读变化和父子回写复用活动草稿门禁。晚到任务按文档代际和请求序号丢弃，不能写入后来活动文档。只读采样和工具/查看偏好不制造文档 dirty。分组队列若有不同语义必须在具体设计中声明，不虚构跨文档原子事务。

## 内容、协议与核验

逐能力同步参数解码、唯一命令门、WASM、React、内容身份、工程序列化、TS 检查和原生核验器；实际接通后才发布能力，不把整个命令前缀放开。共享限制只在 `rust/project-limits.json` 与两端 fixture 中维护；不整体提升现有 8192 单边、64 图层、64 MiB 工程、16 嵌套深度和 8 文档上限。

新增规范内容缺省/空值保持旧工程身份兼容，工具本机设置/视图不进入内容 hash。涉及新持久字段时必须给出与旧运行时的能力协商、解码前累计预算和资源引用验证；未知内容不能通过通用 JSON/PSD 原始块绕过。PSD 与 LayerTransferBundle 的兼容项逐类型更新，无法表达时报告而非静默压平。

## 取舍与发布条件

优先复用上游算法和现有 UI/草稿，避免复制另一套内容状态。不能编译进 WASM、没有 codec/字体/硬件或缺公共端口的子能力单独记录停止原因，不能因此把整个域标为完成。

原生路径保存/恢复、持续目录监听、PSB、ICC/CMYK/HDR 和依赖未编入 WASM 的解码器暂缓；不承诺所有上游格式双向可用。

## 验收主线

在真实 WASM 逐格式打开 → JPEG/WebP/TIFF 真实编码预览 → 逐层/按名称资产交付；缺 codec、伪扩展名、包超限和取消分别验证。 具体成功/失败情景和逐项证据见 specs 与 verification；实际像素、结构、历史和工程往返都通过后才开放相应子能力。
