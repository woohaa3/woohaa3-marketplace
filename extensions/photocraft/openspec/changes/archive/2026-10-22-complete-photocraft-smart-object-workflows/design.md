# 智能对象子文档与还原图层设计

## 基线与范围

固定上游 commit `4e7a17cd5d5723313f459753663d0d155f047e19`；已提交实现 `bdc3c0847fa7d2ed5db82128dafcf3f47ad1bfa1`。范围逐项列于 [scope.md](scope.md)，每个 U 组的子能力都需拆成实现时的命令/参数/操作记录，不以一组一个按钮结案。

同级前置：无新增同级 change 的硬依赖。相邻模块只是消费端口的软依赖时，以现有内核能力完成基础流程，新增联动在两边均交付后验证。原 change 的未验收项仍按其证据处理；本计划仅追加缺口，不自动勾选或重写旧任务。

## 操作与布局

选中智能对象即可在属性/右键进入替换、导出、编辑内容或转回图层；子文档完整显示菜单、工具和返回/更新父文档操作。

复用固定上游 0.9.0 的生产算法，不修改 vendor。`rust/crates/editor-core` 持有规范内容、命令、预览草稿、身份与历史；`packages/protocol` 持有纯数据和限额契约；`packages/editor` 持有共享工具/面板。`dev` 与 `integrations/woohaa` 只装配公共端口，核心不得 import Woohaa 私有实现或内部工具。

界面沿用既有菜单 → 工具组 → 参数栏 → 原图/属性反馈的结构，菜单和参数栏在文档标签之上。所有状态均需有可见忙碌、失败与恢复反馈；面板仍使用现有浮动/停靠能力，不重新设计外壳。只验收电脑 1440×1000 和 Pad 正常窗口 1024×768；手机/极窄窗口和无障碍专项不在范围。

## 本域实现决策

### D1

对象可用性由选中层/source 和宿主端口决定；state.active 只表示当前子会话，不控制父层替换/导出入口。以文档/编辑器根实例限制宿主定位 CSS，不能把父级后代选择器套到嵌套编辑器内部。

### D2

沿用既有 parent/sourceHash/baseRevision/attemptId 关联及幂等回写，不重建第二个子文档系统。父子保存/切标签/关闭均经门禁，导出源不等于回写父对象，替换保持实例变换。

### D3

Convert to Layers 先验证嵌入工程并解包为候选组，应用源到实例的布局、样式与蒙版规则；重映射层/资源 id。当前实例解包不能修改其他共享实例；有活动子草稿时先结算或拒绝，超过层数不退化栅格化。

### D4

「转回图层」只解包当前实例，工程里其他共享实例仍是智能对象，因此保存与重开都必须接受这类工程，否则 U66 的成功证据「其他共享实例不变」在宿主里无法成立。两侧采用同一形状：先走收紧的普通口径，**只在它因嵌入智能对象而拒绝时**才回退到含源通道，普通上传、CLI 与其他拒绝原因完全不变。

- 编辑器：`Editor::open_project` 先用 `photocraft_project_verify::verify()`，失败后才试 `smart_source::verify_project()`（根容器与整棵源树同一预算，继续拒绝外链、未开放效果、坏名称与不可逆仿射）。
- 宿主：Media 的工程 ingest 先用 `verifyForIngest()`；仅当错误码是 `unsupported-object` 且外层 `inspectEmbeddedPhotocraftProject` 确认 `objectKinds` 含 `smart` 时，才改走 `verifyEmbeddedForIngest()`（外层结构加原生 `--embedded-smart` 摘要逐项一致）。

失败语义：未配置原生核验工具时含源工程拒绝保存（fail closed），不退化成「只凭外层结构通过」；任何其他拒绝原因都原样返回，不被回退吞掉。

## 事务和生命周期

内容操作遵守 begin → preview → commit/cancel：固定 documentId/generation、baseRevision、目标及 attemptId；预览不变正式内容 hash/修订/历史，确认最新有效候选一次，取消恢复，无变化不新增历史。非法参数不得确认上一份成功预览。一次笔迹/拖动按既有完成规则提交，不强制所有参数都变成弹窗。

保存、切文档、关闭、只读变化和父子回写复用活动草稿门禁。晚到任务按文档代际和请求序号丢弃，不能写入后来活动文档。只读采样和工具/查看偏好不制造文档 dirty。分组队列若有不同语义必须在具体设计中声明，不虚构跨文档原子事务。

## 内容、协议与核验

逐能力同步参数解码、唯一命令门、WASM、React、内容身份、工程序列化、TS 检查和原生核验器；实际接通后才发布能力，不把整个命令前缀放开。共享限制只在 `rust/project-limits.json` 与两端 fixture 中维护；不整体提升现有 8192 单边、64 图层、64 MiB 工程、16 嵌套深度和 8 文档上限。

含智能对象的工程需要两个独立的接收面同步（见 D4）：编辑器打开走 `verify_for_open`，宿主保存走 `verifyProjectForSave`。两者都不是「放宽核验」，而是把同一套预算的含源通道接到正确的入口；普通上传、CLI 与旧运行时的收紧口径必须保持可验证（`open_project_still_rejects_unrelated_verification_failures`、`open_project_keeps_layer_budget_for_embedded_sources`、`project-ingest.test.ts` 的 4 个用例）。

新增规范内容缺省/空值保持旧工程身份兼容，工具本机设置/视图不进入内容 hash。涉及新持久字段时必须给出与旧运行时的能力协商、解码前累计预算和资源引用验证；未知内容不能通过通用 JSON/PSD 原始块绕过。PSD 与 LayerTransferBundle 的兼容项逐类型更新，无法表达时报告而非静默压平。

## 取舍与发布条件

优先复用上游算法和现有 UI/草稿，避免复制另一套内容状态。不能编译进 WASM、没有 codec/字体/硬件或缺公共端口的子能力单独记录停止原因，不能因此把整个域标为完成。

外链智能对象、任意路径重链接和智能滤镜栈保持 NON_GOALS。

## 验收主线

不打开子文档直接替换/导出源 → 子界面完整编辑回写 → 共享实例中只对一个转回层 → 重开并验证撤销/冲突恢复。 具体成功/失败情景和逐项证据见 specs 与 verification；实际像素、结构、历史和工程往返都通过后才开放相应子能力。
