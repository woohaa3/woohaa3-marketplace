# 图像模式与调色板设计

## 基线与范围

固定上游 commit `4e7a17cd5d5723313f459753663d0d155f047e19`；已提交实现 `bdc3c0847fa7d2ed5db82128dafcf3f47ad1bfa1`。范围逐项列于 [scope.md](scope.md)，每个 U 组的子能力都需拆成实现时的命令/参数/操作记录，不以一组一个按钮结案。

同级前置：2026-10-22-add-photocraft-channel-workflows。相邻模块只是消费端口的软依赖时，以现有内核能力完成基础流程，新增联动在两边均交付后验证。原 change 的未验收项仍按其证据处理；本计划仅追加缺口，不自动勾选或重写旧任务。

## 操作与布局

图像 → 模式 / 颜色表 / 陷印；只修改本域模式控制器，其他工具经稳定目标能力接口决定是否可用。

复用固定上游 0.9.0 的生产算法，不修改 vendor。`rust/crates/editor-core` 持有规范内容、命令、预览草稿、身份与历史；`packages/protocol` 持有纯数据和限额契约；`packages/editor` 持有共享工具/面板。`dev` 与 `integrations/woohaa` 只装配公共端口，核心不得 import Woohaa 私有实现或内部工具。

界面沿用既有菜单 → 工具组 → 参数栏 → 原图/属性反馈的结构，菜单和参数栏在文档标签之上。所有状态均需有可见忙碌、失败与恢复反馈；面板仍使用现有浮动/停靠能力，不重新设计外壳。只验收电脑 1440×1000 和 Pad 正常窗口 1024×768；手机/极窄窗口和无障碍专项不在范围。

## 本域实现决策

### D1

灰度/位图/索引色/双色调为真实模式而非黑白调整近似。先实现模式字段、调色板/油墨数据、有界转换和现存 RGB 工具的允许矩阵，再开放对应入口；不可表示的层要求显式副本转换。专色仅使用屏幕替代表示，不扩 ICC/CMYK。颜色表及陷印属于该模式矩阵。

### D1a 计划 → 应用，而不是长草稿

本域没有引入新的活动草稿状态，而是把转换拆成两步纯计算：

- `planMode(target, params)` / `planColorTable(params)` 在**独立 scratch 会话**（克隆 `DocState`）上跑完整上游命令，返回报告 + 源像素预览（base64 RGBA）+ `baseRevision`/`baseContentHash`，正式文档、修订、历史与内容指纹都不动；
- `applyMode` / `applyColorTable` 先核对基线（修订与内容指纹都必须一致），再在同一 scratch 上重算候选，最后用一次 `preview_history::commit` 提交一步历史；候选与当前状态相同时 `changed=false`，不提交、不新增历史。

这样做的原因：共享的 `Editor` 草稿字段、工具草稿门禁、保存/切文档门禁都由集成负责人维护，本域不应为了预览去改它们；重算候选是确定性的，不需要在内核缓存候选像素或计划 id。代价是确认时多做一次转换（预览单边 ≤1024、应用时不再生成预览），换取「预览永不污染正式文档」和「晚到计划不可能写到已变化的文档上」。

界面侧同样遵守这条边界：**任何参数改动都立即作废当前预览**，必须重新预览才能确认，因此非法最后输入不会提交上一份成功候选。

### D1b 共享改动已落地（内容身份、发布、入口、核验、门禁）

早期计划把五项共享改动列为「交付给集成方」。用户明确授权修改必要共享文件后，这些改动已在本 change 内完成，不再有待交接项：

1. **内容身份**：`document_content::project_content` 写入 `mode` 字段，`identity::canonicalize` 在 `canvas:`/`patterns:` 之后、图层之前追加模式行，协议侧 `canonicalizeImageProjectContent` 同序同文本。身份文本由 `features/modes/content.rs` 与 `packages/protocol/src/features/modes/content.ts` 共同产出（`mode:<id>[:depth]`、`|table:<n>:<#rrggbb,…>`、`|transparent:<i>`、`|inks:<n>:<len>:<name><#rrggbb>#<pts>`），数值一律整数化（8 位色 0..255、油墨/曲线 0..10000）避免浮点格式化协商；两端共读 `content-fixtures.json` 做 parity。
   **缺省 RGB/8 位/无表/无油墨不产生任何行**（显式 `null` 与省略等价），旧工程指纹逐字节不变，因此不需要事后迁移。实测改表、改油墨、灰度→双色调三者现在都会改 `contentHash`。
   范围外颜色模型（CMYK/Lab/多通道）**完全不产生模式行**：早期版本折成 `{"mode":"other"}` 被 `canonicalize_mode` 判为不可判定，导致整份指纹为 `None`、`modeInfo`/`contentHash` 直接报 `no-document`。这是复核中发现的真实回归（自己引入、自己修的），现有 `colour_models_outside_the_change_scope_still_have_a_content_hash` 回归锁定。
2. **能力与命令发布**：`features/modes/mod.rs` 的 `CONTRIBUTION` 现在是真实 P7 贡献（`image.modes`/`image.color-table`/`image.duotone`，order 40/41/42）与六条 `image.mode.*` 命令（order 40–45）；协议 `features/modes/index.ts` 的发布清单、`tests/fixtures/contract.json`（能力 71→74）、WASM 基线三处同步。真实 WASM 握手实测含 74 项且末尾为三个新模式 id；`image.mode.grayscale` 经 `execute` 真实放行。
3. **菜单入口**：`sections.tsx` 注册「图像 › 模式与颜色表…」，`boundaries.test.ts` 的 section 总数 12→13 并断言 `modes` 有 section。
4. **原生核验接入**：`verify_container_with` 在样式校验后调用 `features::modes::validate_document`，各入口的 4 处 `#[cfg_attr(not(test), allow(dead_code))]` 已移除。核验规则**刻意不比编辑器更严**（不校验位深/像素格式，接受 CMYK/Lab/U16），否则会出现「编辑器能存、核验说坏」的假失败。
5. **跨域命令门**：见 D1c，已在内核真实生效。

### D1c 工具矩阵与跨域门禁（实测驱动，不是推测）
**判据是「写进去的颜色该模式能不能表达」，不是「索引色禁止绘制」这种粗规则**——后者会连掩版、选区与几何操作一起挡掉。实测结论：

| 模式 | 能否表达任意写入 | 结论 |
| --- | --- | --- |
| 索引色 | 否：抗锯齿边缘本身就出表，内核也不量化 | 拒绝写颜色的命令 |
| 位图 | 否：只有黑白两点合法 | 拒绝写颜色的命令 |
| 灰度 | 是：上游把彩色收敛为灰阶（`nonGray=0`） | 不拒 |
| 双色调 | 是：同样收敛为灰阶再由油墨映射（`nonGray=0`） | 不拒 |
| RGB / 范围外颜色模型 | — | 不拒（本域不判定） |

被拒命令族：`paint.*`（`target:"mask"`/通道目标除外）、`type.*`、`edit.fill*`、`path.fill`/`path.stroke`、`filter.*`、`image.adjustments.*`、`layer.newAdjustmentLayer.*`、`layer.rasterize.*`。掩版、通道、选区、图层结构、几何变换与读取类命令**永不拒绝**。灰度/双色调不设限不是偷懒：实测彩色笔迹在灰度文档上留下 `nonGray=0`，挡掉它是无谓的功能损失。

门禁挂**所有写入口**，不只是命令分派：`Editor::execute`（唯一命令门之后、任何草稿/预览分支之前）、`begin_stroke`（否则用户画完一笔才在提交时被拒）、`begin_text` 与 `begin_filter`（它们走各自的 scratch 会话，不经命令分派）。因此快捷键、命令面板与宿主脚本都无法绕过。

**复核中发现两处界面与内核不一致**，都是本次改动引入的，已修：

- 索引色矩阵原本允许 `clone`/`heal`，但它们是 `paint.*`，门禁会拒绝 → 界面说可用、点了必失败；
- 双色调矩阵原本关闭 `text`/`pen`，但实测文字在双色调里收敛为灰阶、不破坏不变量 → 界面声明了一个不存在的限制。

修法不是各改各的，而是让两侧共读同一份契约：`packages/protocol/src/features/modes/gate-fixtures.json` 定义工具 → 代表命令、各模式关闭集合与写色命令清单，Rust `features::modes::gate` 与 TS `modeToolAvailability` 的测试逐项核对，因此不可能再出现单向漂移。

面板文案随之从「建议保持关闭 / 尚未接通」改为「当前模式不可用 …（内核会拒绝）」「这些限制由内核强制：命令与草稿入口都会拒绝，并说明原因」。把已生效的限制说成建议，与把未生效的限制说成已生效一样是假话。

油墨与颜色表都是真实持久内容，面板不能用自己的默认值代替文档里的值：打开已有的双色调文档时从 `modeInfo().duotone.inks` 载入名称/颜色/曲线，类型由油墨数量推导（1/2/3/4 → 单/双/三/四色调）；仅新建双色调或用户主动增加油墨数量时才用与内核 `default_inks` 逐项一致的默认油墨。这条在复核中发现是真实缺陷（原实现会覆盖用户油墨），已修并有回归。颜色表预设会整表替换（`web` 只有 216 条），旧的透明索引可能因此越界并被内核拒绝，所以切到预设时清空透明索引、切回自定义由用户重新指定；这条同样来自实测而非推测。

导出矩阵同理，且与真实编码器逐项核对过：索引色写出 8 位调色板 PNG（实测 PNG `colorType=3` 且带 `PLTE`），双色调与 RGB 写出 RGB PNG，灰度与位图写出灰度 PNG；**PSD 只对 RGB/U8 开放**，其余四种模式在共享 PSD 预检阶段就被拒绝（`PSD 导出只支持 RGB/U8 文档`），因此面板对它们显示关闭及真实原因，不承诺一个必然失败的入口。双色调的 PSD 油墨块与 Photoshop 往返仍未验收，属外部应用项。

位图文档的只读读数仍报 `depth=8`，因为内核把黑白像素按 8 位通道展开存放（`modeInfo().depth` 是通道采样位深，不是文件的 1 位/像素）。面板对位图模式额外注明这一点，否则「位图 · 8 位/通道」看起来像转换时悄悄改了位深——这与「不静默降位深」的承诺相冲突。

### D1d 归属键用「代际 → 修订 → 内容指纹」三层判据

计划的 `baseRevision` 只能识别同一份文档的后续编辑：两份新文档都可能是修订 1，切过去以后修订号依旧匹配；内容指纹能挡住「同修订的另一份内容」，但**挡不住关闭后重开同一节点**——那可能又是修订 1、指纹也逐字节相同，而前一计划来自已经销毁的会话。因此归属判据做成三层：

1. **文档代际**：控制器接受宿主的 `documentId` 与 `documentGeneration()`（Woohaa 适配包传注册表条目 id 与条目 `generation`），并在每次成功载入文档（`openImage`/`openProject`/`openPsd`）时自增自己的载入代际。计划由工作区盖 `owner{documentId,generation}`，确认时先比这一层；
2. **修订**：`baseRevision` 与当前视图修订比对；
3. **内容指纹**：`handle.contentHash()` 与计划的 `baseContentHash` 比对（内核在应用时还会再核一次）。

面板也以 `documentOwner()` 的 `documentId#generation` 参与文档键：代际变化即丢弃上一份预览，不能留着「不属于当前文档的报告」还允许确认。这样「来源失效不误写目标」在域内、真实控制器与宿主三层都是可测的（`workspace.test.ts`、`modes-workspace-gate.test.ts`、宿主 `document-session.test.ts`/`editor-workspace.test.ts`）。

### D1e 运行时协商与界面状态一致性

「加载旧运行时」这条 spec 场景不能靠调用报错来体现：直接调用缺失的导出会抛 `TypeError: xxx is not a function`，界面上只是一句英文开发者信息，用户看不出是内核版本问题、也不知道该怎么做。适配层因此在每次调用前核对本域 5 个导出（`modeInfo`/`planMode`/`applyMode`/`planColorTable`/`applyColorTable`），缺失时返回 `runtime-unsupported` 并逐项列出缺什么、提示升级内核；协商通过后非法响应仍照原样失败，不会因为加了这一层就「什么都说行」。

界面侧有两条同类的「界面状态与真实结果不一致」约束，都来自复核而非推测：**双色调曲线不足 2 点时内核静默退回恒等曲线**，所以删除与添点都必须保证留下来的形状是可保存的（删到 <2 点清空，从 <2 点添点一次补成 `[[0,0],[100,100]]`）；**灰度文档的默认目标本身就是不可用的「灰度」**，面板一打开预览就是禁用且无任何用户操作能解释，因此只在文档/模式首次变化时把目标纠正为第一个可用目标，同一文档后续编辑不顶掉用户特意选中来读原因的目标。

## 事务和生命周期

内容操作遵守 begin → preview → commit/cancel：固定 documentId/generation、baseRevision、目标及 attemptId；预览不变正式内容 hash/修订/历史，确认最新有效候选一次，取消恢复，无变化不新增历史。非法参数不得确认上一份成功预览。一次笔迹/拖动按既有完成规则提交，不强制所有参数都变成弹窗。

保存、切文档、关闭、只读变化和父子回写复用活动草稿门禁。晚到任务按文档代际和请求序号丢弃，不能写入后来活动文档。只读采样和工具/查看偏好不制造文档 dirty。分组队列若有不同语义必须在具体设计中声明，不虚构跨文档原子事务。

宿主侧的门禁以控制器的 `blockingDraft()` 为唯一权威（`pendingDraftFailure()` 暴露给适配包，`pendingDraftOf` 不再自己列一遍草稿种类），因此「保存会拒绝、切标签却放行」这类不一致没有第二份清单可以漂移。冻结/保存阶段对模式写入返回 `frozen`：已冻结的修订上继续改内容会让回执与内容不符。

## 内容、协议与核验

逐能力同步参数解码、唯一命令门、WASM、React、内容身份、工程序列化、TS 检查和原生核验器；实际接通后才发布能力，不把整个命令前缀放开。共享限制只在 `rust/project-limits.json` 与两端 fixture 中维护；不整体提升现有 8192 单边、64 图层、64 MiB 工程、16 嵌套深度和 8 文档上限。

新增规范内容缺省/空值保持旧工程身份兼容，工具本机设置/视图不进入内容 hash。涉及新持久字段时必须给出与旧运行时的能力协商、解码前累计预算和资源引用验证；未知内容不能通过通用 JSON/PSD 原始块绕过。PSD 与 LayerTransferBundle 的兼容项逐类型更新，无法表达时报告而非静默压平。

## 取舍与发布条件

优先复用上游算法和现有 UI/草稿，避免复制另一套内容状态。不能编译进 WASM、没有 codec/字体/硬件或缺公共端口的子能力单独记录停止原因，不能因此把整个域标为完成。

LUT、ICC/CMYK/Lab/HDR、16/32 位与真正 RAW 解码不进入本次范围；陷印需要 CMYK，本次范围排除，入口保持关闭并给出原因。

索引色/双色调的实现、身份、核验、菜单入口与跨域门禁均已接通；仍未验收的是真实 UI 走查（需要显示会话）、通道域联合验收（同级依赖端口未落地）与 Photoshop 双色调往返（外部应用）。这三项在 `tasks.md`/`verification.md` 中保持未勾选并写明真实原因，不用自动化结果冒充。

## 验收主线

RGB 转灰度/位图/索引色/双色调 → 调色板编辑 → 保存重开 → 支持的工具和导出拒绝矩阵；不静默降位深或压平。 具体成功/失败情景和逐项证据见 specs 与 verification；实际像素、结构、历史和工程往返都通过后才开放相应子能力。
